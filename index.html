How I Work

My Backlog Triage Process

Most Product Owners relay reports. I verify first — which means most of what lands on developers' plates is already diagnosed, and a lot never reaches them at all.

1

A demand comes in

A production or business stakeholder reports something wrong — a number that looks off, a process that isn't behaving as expected, a report that doesn't match what they see on the floor.

2

I check the database myself, before anything else

Not the dashboard, not the report — the underlying data directly. Most "bugs" turn out to be explainable once you see what the data actually contains, and I'd rather find that out myself than ask a developer to.

3

Then I split the problem in two

What happens next depends on what the data actually shows:

Data / analysis issue

Wrong calculation, bad or missing data, a metric defined incorrectly — I fix it directly myself and report back to the requester. No ticket, no wait, no developer time spent on something that was never a code problem.

Real software issue

An actual bug or a genuine feature change — I dispatch it to the dev team, already diagnosed: what's wrong, where, and what the data showed, so the ticket that lands on their desk is specific and actionable, not "something's broken, please look."

This is the exact process behind the dashboard-bug and planning-incident case studies below — both were data issues I traced and fixed myself before they ever became a developer ticket.

Catching a 5.4-Point Error in a Live Production Dashboard

A site-wide "rendement" (yield) KPI card was computing a simple, unweighted average across production groups — letting one small, high-performing group distort the figure for the entire site.

  • For one site/date combination, the dashboard reported 54.59% — the actual, correctly weighted figure (by minutes worked) was 49.18%, a 5.4-point gap caused by a single 1,939-minute group running at 100.6% pulling the average up against six much larger groups averaging closer to 47%.
  • Fixed with a weighted aggregation (SUM(value × weight) / SUM(weight)), the same technique already used correctly elsewhere in the same dashboard — so the bug was an inconsistency, not a missing capability.
