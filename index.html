How I Work

How I Approach Production Issues

I investigate reported ERP issues at the data level before escalating them — comparing database records, business rules, and application behavior to distinguish a data-quality or calculation issue from a genuine software defect.

1

A demand comes in

A production or business stakeholder reports something wrong — a number that looks off, a process that isn't behaving as expected, a report that doesn't match what they see on the floor.

2

I check the database myself, before anything else

Not the dashboard, not the report — the underlying data directly. Most "bugs" turn out to be explainable once you see what the data actually contains, and I'd rather find that out myself than ask a developer to.

3

Then I split the problem in two

What happens next depends on what the data actually shows:

Data / analysis issue

Wrong calculation, bad or missing data, a metric defined incorrectly — I identify the cause, validate the correction, and document the resolution through the appropriate process, without routing it through the dev backlog for something that was never a code problem.

Real software issue

An actual bug or a genuine feature change — I dispatch it to the dev team, already diagnosed: what's wrong, where, and what the data showed, so the ticket that lands on their desk is specific and actionable, not "something's broken, please look."

This is the exact process behind the dashboard-bug and planning-incident case studies below — both turned out to be data issues, resolved through validated, documented corrections rather than a development ticket.

AI-assisted delivery

I use LLM tools to accelerate SQL/Python development, debugging, specification drafting, and technical documentation. I validate generated output against business rules and system behavior, particularly when working with production data. AI supports my workflow; technical judgment and delivery accountability remain mine.

A client's legacy ERP replaced with Textilys — planned at 6 months, delivered in 3. The compression wasn't a shortcut, it came from collapsing a project that's normally split across separate specialists (a functional analyst, a migration engineer, a trainer) into phases I ran myself or drove directly, so nothing sat waiting on a handoff or someone else's calendar.

  • Functional comparison first: mapped Textilys against the client's old ERP feature by feature to find the real functional gaps, before any code moved.
  • Led the dev team through the adaptation: turned those gaps into specifications and coordinated directly with developers to adapt Textilys to cover what the client actually needed — this was a team effort I drove, not solo work.
  • Owned and ran the data migration, in parallel with the dev work rather than after it, using AI-assisted development for the tooling and validating the results against the data: a CLI engine that introspects both schemas live (no hardcoded table list), loads tables in dependency order, pre-checks every column for blocking issues before touching data, and reconstructs one table from a business rule instead of copying it directly.
  • Trained every level on-site: from the director down to floor operators, explaining what changed and why, in terms that matched how each group actually used the old system.
  • Approved the go-live myself: signed off the production cutover once the migration checks and user acceptance testing had passed.
  • Outcome: the client has been running on the new system since October 2026, with ongoing support.

Before this — my first rollout (go-live 10/2025): on an earlier client deployment I worked on the functional side. My functional testing is what cleared the system for go-live, and that project is where I learned the database side I then used to run this one end to end.

KPI Dashboard — From Stakeholder Wireframe to a Bug Caught Live

Textilys · Metabase · 2026

Requirements gathering → spec → team sign-off → live data quality

Started from a hand-drawn, 2-page wireframe sketched by stakeholders in a requirements meeting. Translated it into a structured spec — mapping every proposed KPI against what data already existed versus what had no source yet, resolving real ambiguity in the sketch with the business directly (one dimension read as "chaîne" turned out to actually mean "Groupe," the team's real unit of work) — and took it to a team architecture review for formal sign-off, open questions flagged rather than hidden.

Once live, the same discipline caught a real bug in production: a site-wide "rendement" (yield) KPI card was computing a simple, unweighted average across production groups — letting one small, high-performing group distort the figure for the entire site. For one site/date, the dashboard reported 54.59%; the actual, correctly weighted figure (by minutes worked) was 49.18% — a 5.4-point gap caused by a single 1,939-minute group running at 100.6% pulling the average up against six much larger groups averaging closer to 47%. Fixed with a weighted aggregation (SUM(value × weight) / SUM(weight)), the same technique already used correctly elsewhere in the same dashboard — an inconsistency, not a missing capability.
